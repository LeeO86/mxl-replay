# mxl-replay — implementation plan

This is the map from `SPECIFICATION.md` draft v0.1 to the tree, including every place the code does not follow a sentence literally.

## Pins

| Piece | Pin |
| --- | --- |
| MXL | `dmf-mxl/mxl` `218ddaa0a08c12ffe75fc475ae65aa3d9eef16d7`, fabrics off |
| nmos-cpp | `fe303849527394b03bdedc8f161f377fe458bb62` |
| JPEG | libjpeg-turbo, 8-bit 4:2:2 |
| UI | Vue 3 + Vite, one embedded HTML file, no CDN |
| MediaMTX | `bluenviron/mediamtx:1.20.1`: its `/mediamtx` binary and `LICENSE` are copied into the image (1.4.0) |
| Tests | doctest (vendored) |

Grain index math is the same 128-bit rounding as MXL at that pin (`src/media/timebase.cpp`). Index 0 is the epoch. A unit test checks index 0 at t = 0 and index 1 at the rounded 30000/1001 period.

## Layout

```
src/config        env > file > default, exit 78
src/media         v210, JPEG 4:2:2, scale, ANC timecode, audio, FFmpeg upload, preview mosaic canvas
src/flow          DIS port (CPU reference) and CUDA blend/pack
src/record        ring buffer, segment files, phased HFR
src/playout       scheduler, shotbox, clip end actions
src/library       SQLite WAL catalog
src/domain        MXL root scan, mirror rejection
src/nmos          UUIDv5 ids; nmos-cpp node when REPLAY_WITH_NMOS=ON
src/mxl           readers and writers when libmxl is found
src/ops           HTTP, WebSocket, Prometheus text, preview plan and widgets, H.264 publisher, MediaMTX child
src/app           recorder + playout engine
web/              Vue 3 UI: one component per tab in web/src/components, shared state in store.js
```

`replay-core` is what the unit tests link. `mxl-replay` is the process.

## Deviations

1. **JPEG storage is 8-bit 4:2:2.** nvJPEG encodes and decodes that on the device when a GPU is visible. libjpeg-turbo is the fallback used for clip playback with no device, and for unit tests. nvJPEG's baseline encoder does not offer 10-bit or 12-bit 4:2:2, so `jpegSupports10Bit()` and `jpegSupports12Bit()` stay false. Status reports `"jpeg":"nvjpeg"` or `"libjpeg-turbo"`.
2. **Reverse playback is implemented** from −100% to 0%. The scheduler already takes a signed speed, so leaving it out would have been the larger change. The UI speed fader is 0–200% as specified; the API accepts a negative speed.
3. **`interpolate` on a CPU-only process falls back to `blend`.** The spec limits the CPU fallback to repeat and blend. Set `REPLAY_ALLOW_CPU_INTERP=true` to run the same DIS port on the CPU (tests and the harness). A visible CUDA device selects the GPU blend path.
4. **OFA is probed, not wired as a second GPU context.** `ofaProbe()` dlopens `libvulkan.so.1` and looks for `VK_NV_optical_flow`. There is no CUDA–Vulkan external-memory interop in this cut, so a machine that has the extension still uses `dis-cuda` for pixels. `NVIDIA_DRIVER_CAPABILITIES` should add `graphics` before that interop is turned on. This was not verified on an A4000 or L4.
5. **The Futatabi OpenGL binary is not built in default CI.** `mxl-replay-harness` compares PPM frames (PSNR / SSIM, 40 dB gate) and can render the port. `docs/benchmarks/README.md` is the procedure for the original-versus-port run. The unit test that shifts a Gaussian clears 40 dB against a ground-truth midpoint; that is not the Futatabi comparison.
6. **A4000 / L4 channel counts are not measured here.** The targets in specification §6.3 stay the acceptance bar. No number in the README is a measured result.
7. **AMWA NMOS Testing** is `tests/nmos/amwa.sh`, not a default CI job. CI starts the node only when `REPLAY_WITH_NMOS=ON`.
8. **Query API port defaults to `NMOS_REGISTRY_PORT + 1`.** `NMOS_QUERY_ADDRESS` and `NMOS_QUERY_PORT` override it. Same default as the other media functions.
9. **Unknown environment variables are ignored.** The config file still rejects unknown keys, so a stray `NMOS_CPP_REF` in the CI environment does not exit 78.
10. **Segments are one MXLR file per 10 s**, not one file per JPEG. The write is sequential and buffered: a finished segment starts its writeback at once (`sync_file_range`) and leaves the page cache at the next rotation (`posix_fadvise(DONTNEED)`). Since 1.1.0 `REPLAY_ODIRECT` is accepted and ignored with a warning (`odirect_ignored`): `O_DIRECT` needs aligned buffers, and the 1.0.x writer's unaligned writes did not work with it.
11. **Export is a JPEG sequence plus WAV**, not ProRes 422 HQ. Upload conversion does use FFmpeg and stores the result as the same JPEG + PCM clips the buffer uses.
12. **Phase order is receiver order.** Phase k is the k-th video receiver of the camera. A custom permutation list is not a separate key.
13. **One image, GPU when the toolkit injects a device.** `docker/Dockerfile` builds on `nvidia/cuda:12.8.2-devel` and the runtime stage carries `libcudart` and `libnvjpeg` only. `libcuda` comes from the NVIDIA container toolkit (`--gpus all`, or `runtimeClassName: nvidia`). Without a device the same binary records and plays with libjpeg, repeat, and blend. CI compiles that same CUDA binary (`ldd` must show `libnvjpeg`); it does not publish a second CPU image. On the device path the host sees the JPEG bitstream and the finished v210 grain. Search, refinement, blend, and packing stay in device memory, and the flow pair is cached there. `.github/workflows/container.yaml` publishes `ghcr.io/leeo86/mxl-replay:nightly-dev` from `main`, `git-<sha7>` on every published build, and `X.Y.Z`, `X.Y`, `X` from a `vX.Y.Z` tag. `nightly-dev` is the only tag that moves.
14. **The default output domain id matches the NMOS domain id** (`mxl-replay/<seed>/domain`). A deployment that previously relied on the shorter derived id without setting `MXL_OUTPUT_DOMAIN_ID` gets a new domain directory. The platform sets the id explicitly.
15. **Config export is one JSON document.** The earlier `KEY=value` body is not returned. `POST /api/v1/config/import` accepts the JSON document.
16. **The catalog lives in `REPLAY_STATE_DIR` (default `/config`).** An `index.sqlite` still sitting in `REPLAY_STORAGE_DIR` is copied across on the first start.
17. **Retention deletes whole segments** instead of overwriting the oldest ones in place. A segment goes when its newest frame is older than the camera's buffer duration behind the newest recorded frame and no clip touches it. Disk use stays at the duration plus one segment plus the clips. Segment names carry the first frame's TAI (`seg-<20 digits>.bin`), so a restart orders them without an index file; the 1.0.x files (`cam<N>_seg<k>.bin`, write-only, renumbered on every start) are removed at the first start.
18. **Camera audio rides on the video frames** (1.2.0). The phase-1 reader reads, for video grain N, the samples `[audioSamplesUntil(N), audioSamplesUntil(N+1))` of the camera's audio flow (MXL addresses them by their end index) and stores them with frame N as interleaved stereo: the first two channels, mono doubled. A flow that is not 48 kHz sets the audio receiver to `unsupported`. Playout reads the audio of the frame on the house time nearest the position (phase 1 of an HFR camera) and writes the output samples at their sample index, one ring per channel. Same `[index-count, index)` convention as mxl-decklink.
19. **Uploads have their own buffer** (1.2.0): `library/frames`, camera `0` (`kLibraryCamera`). A camera buffer only appends, so the 1.1.0 uploads at TAI 1 ns onward were refused once the camera had recorded. Uploads are placed on the frame grid after the library's newest frame; a retention of 1 ns keeps only the segments a clip touches, and deleting a clip frees them. Clips uploaded with 1.1.0 keep camera 1.
20. **Start order is HTTP, index, NMOS, MXL** (1.2.0). `Engine` checks the storage and opens the catalog; `openBuffer()` indexes the segments and protects the clips again. Until then every path except `/livez` answers 503 `indexing`.
21. **The clip cap counts kept segments** (1.2.0): `FrameRing::protectedBytes()` is the size of the segments a protected range overlaps, because a clip keeps whole segments.
22. **No disk I/O under the engine lock** (1.2.0). `FrameRing` has its own lock for the index; reads use a duplicate of the cached descriptor after the lock is released, and the single writer (serialised by a second mutex) writes without it. The engine releases its lock for recording writes, channel frame and audio reads, and exports. The CPU fallback still JPEG-encodes under the engine lock (only without a GPU). A janitor thread per buffer starts the writeback of a finished segment (`sync_file_range(SYNC_FILE_RANGE_WRITE)`), drops the one before from the page cache and deletes expired files: on the lab's SAS disk the writeback start alone blocked for up to 1 s (strace, 4 cameras at 1080p50).
24. **Playout is locked to the TAI grid** (1.2.0). Each channel thread renders grain N for `indexToTimestamp(N)` and sleeps until grain N+1 starts; more than two grains late, it continues at the current grain. Live position is then exactly `N - REPLAY_LIVE_DELAY_FRAMES` (an exact pick, no interpolation), and every grain index is written once.
25. **Late camera audio is waited for** (1.2.0, 1.2.1): up to one frame (`mxlFlowReaderGetSamples` with a timeout) until three reads in a row missed; then non-blocking, with one waiting read every 50 frames. A stalled audio flow costs the video at most one frame per 50, and a writer that is always a little late is still picked up.
26. **Live waits for its frame** (1.2.1). The recorder stays two grains behind (reading one behind found the player's audio not yet committed), so frame M−2 becomes readable when grain M starts, the moment a live channel renders it. Render waits up to half a frame (`FrameRing::waitFor`, signalled by `push`) when the camera's newest frame is within three frames before the position; otherwise it does not wait. Lab, 60 windows of 80 frames of live output audio: with the buffer on tmpfs 1.2.0 is already 60/60 clean; on the SAS disk 1.2.0 is 57/60 and 1.2.1 56–58/60, because a `write()` stalled by dirty-page throttling holds up the recorder for 20–30 ms. Not fixed for slow disks (that needs segment writes off the recorder thread); the README requires a dedicated NVMe. Also tried and not released: rendering grains in the middle of their period with the recorder waking at grain boundaries (58/60 and 60/60 on the SAS disk).
27. **CPU path without the engine lock** (1.2.2). Without nvJPEG a camera with one phase encodes on its reader thread with `encodeJpegV210`: v210 lines to 8-bit rows, libjpeg-turbo raw 4:2:2, output written straight into the stored vector, one compressor and its row buffers per thread; the same bytes as `encodeJpeg422(unpackV210(…))` (unit test). HFR phases still go through `ingestVideo` under the lock (their interleave needs it). Playout decodes exact frames with `decodeJpegToV210`; blends decode two 16-bit frames and blend in place without the lock. libjpeg-turbo 2.1 checks its SIMD support through a thread-local variable on every call (`__tls_get_addr`, about 8 % of the CPU path); a static libjpeg-turbo build would remove that and is not done.
28. **CUDA waits block** (1.2.3). `prepareNv` sets `cudaDeviceScheduleBlockingSync` once, before the primary context exists. With CUDA's default (spin while there are spare cores) each thread's `cudaStreamSynchronize` busy-waited: 4 interpolating channels used 7.4 cores, 6.5 of them in libcuda. A blocking wait costs a wake-up of some microseconds per sync, nothing next to a 20 ms grain.
29. **Senders resolve `auto` in `/active`** (1.2.4). Each sender connection gets `[{mxl_domain_id: <output domain>, mxl_flow_id: <its flow>}]` as active parameters when it is created, and `on_resolve_auto` resolves a sender's `auto` to the same values (the flow from the IS-04 sender's `flow_id`). Receivers keep their previous `auto` handling.
23. **Buffers of removed cameras are deleted at startup** (1.2.0), before the space check, unless a clip uses that camera. Only `seg-*.bin` and 1.0.x segment files are removed, then the directory if it is empty.
30. **UI previews are made on request** (1.3.0). `GET /api/v1/channels/{n}/preview.jpg` point-samples the channel's last output grain to 640 pixels across (under the engine lock, about 0.2 Mpixel) and encodes it without the lock; camera previews and clip thumbnails decode the stored JPEG (newest frame, or the clip's IN frame, which must be within one frame period) without the engine lock, with libjpeg's DCT scaling at the smallest of 1/2, 1/4, 1/8 that is still 384 pixels wide (480 × 270 from 1080p). All of this runs on the single HTTP thread, so previews are kept for other UIs: channels 150 ms, cameras 1 s, thumbnails per clip, camera and IN frame (the cache starts over beyond 512 entries). Nothing is spent while no UI asks: the per-frame 32×16 thumbnails are gone (the GPU path's was a crop of the top-left corner, the CPU path's every tenth frame), and so is the unused per-camera thumbnail of the 16-bit recording path. The UI asks five times a second for the LSM monitor and once a second per camera. Lab (1080p, buffer on a SAS disk), median request time: camera picture 12.5 ms with the full-size decode, 5.1 ms made at 1/4 scale, 0.4 ms kept; a thumbnail's first request 10.3 ms, mostly reading the frame from disk. Full-motion monitoring stays with mxl-webrtc-monitor (§8.2).
31. **Timecode in the status is formatted by the server** (1.3.0) with the formatter the ANC uses: house rate, non-drop-frame, TAI time of day. `timecode` is the last output grain's ANC value (source or output per `tc_mode`); `position_tc`, `in_tc`, `out_tc` and the clips' `in_tc`/`out_tc` are source timecodes. The UI does not compute timecode from TAI nanoseconds (JavaScript numbers carry them only to 256 ns).
32. **Playlist entries are played with their own speed, end action and auto-advance** (1.3.0); 1.2.x stored them and used the clip's. A `PUT` while a channel plays the playlist keeps the channel on its entry (the same clip nearest its old place, else the same place); a `PUT` may keep entries whose clip was deleted, only new entries must name existing clips. Auto-advance only matters for the end action `next`: on, the next clip plays at once; off, it is cued (on its IN, paused, shot state `cued`) and the next Play or shotbox click starts it. Entries whose clip was deleted are skipped. `POST /api/v1/playlists` with `clips` still makes entries with `next` and auto-advance.
33. **Shotbox buttons are clips or playlists** (1.3.0). A cue puts the channel on the clip's (or the playlist's first clip's) camera, IN, speed and modes; play from cued or paused continues where the channel stands (1.2.x restarted at IN after a pause); play from idle or ended starts at IN.
34. **Request bodies are parsed as JSON** (1.3.0) by a small reader in `src/util/json.cpp` (numbers keep their literal, so TAI nanoseconds are exact; numbers sent as strings are still accepted). The earlier substring search found keys anywhere in the body and could not read escaped quotes. Config import uses the same reader (escaped names and tags round-trip). Missing or invalid values answer 400 (a channel's speed is −1…2 as the scheduler clamps it; a clip's or playlist entry's speed 0.01…2, because at 0 or backwards it never reaches OUT, and a new clip made at such a channel speed plays at 1), unknown channels, cameras, clips and playlists 404, and `POST /api/v1/clips` 409 only at the protection cap. `HttpServer` answers 500 when a handler throws instead of ending the process.
35. **A clip's new IN or OUT needs a recorded frame within one source frame period and lands on it** (1.3.0; `FrameRing::nearestNs`, an index lookup without a read); otherwise, or when OUT then comes before IN, the edit answers 400. A range outside the buffer could never be freed by retention. A range that grows while clips keep `REPLAY_PROTECT_MAX_PCT` answers 409 unless `force` is set, like a new clip. The new range is protected before the old one is released. `FrameRing::unprotect` removes one matching range, so two clips with the same range keep it until both are deleted. A clip consolidated out of a camera buffer holds no range: it is released once, not again on delete or edit, and not protected again at a restart. Imported clips are protected at once.
36. **The WebSocket pushes the status ten times a second** (1.3.0; every frame before), and never blocks: a client that cannot take a whole message at once is shut down (the poll loop then closes it) and reconnects. Before, `broadcast` sent with a blocking `send` under the connection lock, so one stalled client stopped the push and then the HTTP loop. Accepted sockets also get a 2 s send timeout. Messages over 64 KB use the 64-bit WebSocket length.
37. **A new clip takes the channel's target speed** (1.3.0), reported as `target_speed`. `speed` is the ramp's current value, which only moves while the channel plays, so a speed set on a paused channel was not what the clip got.
38. **Left out of the 1.3.0 UI**: the phase-alignment view of §4.2 (the status has no per-phase pictures; cameras show phase routes and missing phases), editing single settings in place (the API does not say which settings come from the environment, which would override an imported value at the next start; import/export covers it), and a WebHID device test (no controller on the lab; the report layout follows Contour's documented format, see `web/src/hid.js`). WebHID needs a secure context, so it works on https or localhost only.
39. **A grain the source never wrote is not a drop** (1.3.1). The reader waits (MXL TOO_EARLY) when its next grain is not written yet. A writer that starts or resumes later begins past it, and MXL does not mark the gap: for a new writer the slots behind its head stay unwritten (TOO_EARLY while in the ring, TOO_LATE after), and a writer that resumes marks only the last ring's worth as invalid. 1.3.0 waited on each unwritten slot until it left the history and counted it, so a camera connected before its source counted every grain up to the source's first one and started recording from the oldest grain in the ring (lab, with a diagnostic build: first grain read 50 grains behind live, plus a few real drops while the first encodes, 29–189 ms on the A16, caught up). Now a still incomplete grain behind the writer's head (`mxlFlowReaderGetRuntimeInfo`, checked again after reading the head) is skipped, and a TOO_LATE grain is counted only when the reader was not waiting for it, or its last look was longer ago than the history (`(grainCount − 1)` grains of the flow): only then could the writer have written and overwritten it (`ReaderWait`). A reader that falls behind (a stalled encode, a frozen process) counts as before. Not handled: a writer that reopens an existing flow after a crash leaves the previous run's grains in the slots it has not written yet; they read as valid.
40. **A stopped input is visible, and camera audio survives a re-created flow** (1.3.2). On the platform (small, 2026-10-09) both cameras of a replay stopped recording for 5 h with nothing in the log, no drops, and `write_bytes_per_second` still at its start value: a fabrics link down (host-01 to host-03) left the mirrors without grains. The reader waited (TOO_EARLY) the whole time and recorded again on its own when the link came back, as 1.3.1 already did on the lab when a writer pauses, stops, is killed or restarts (test player; fabrics agents restarted, the source agent stopped for 20 s, the mirror flows deleted and created again with new inodes). Now each camera phase has an `InputWatch` (`src/mxl/io.hpp`): when nothing was recorded for `REPLAY_INPUT_STALL_S` (default 2 s) while it is connected, it logs `recording_stopped` once with a reason (`flow_missing`: the flow cannot be opened; `invalid_grains`: grains arrive invalid or incomplete and are skipped; `no_grains`), and the next recorded grain logs `recording_resumed` with `gap_ms`. The reader is not opened again on a timeout: MXL already answers FLOW_INVALID when the flow was removed or created again, and the reader then opens it again (lab: every case above recovered within a second of the first new grain). `record_last_frame_age_seconds` (and `last_frame_age_s` in the status) is the age of the camera's newest recorded frame, counted from the start at most. `write_bytes_per_second` is now what the recorder wrote (JPEG and audio bytes of the stored frames) since the previous `/metrics`, over at least a second; the start-up write test, which it showed before, is `storage_measured_bytes_per_second` (§4.3 still measures it at start). The lab also showed the one case 1.3.1 did not recover: the camera's audio reader ignored FLOW_INVALID and stayed on the deleted flow, so after a writer restart or a re-created mirror the camera recorded on without audio and its audio receiver still said `running`. It now opens the audio flow again on FLOW_INVALID. Not covered: an audio flow alone that stops (video still running) is not logged.
41. **The WebRTC preview is one mosaic, encoded once** (1.4.0, specification §8.6). `REPLAY_PREVIEW_MODE=webrtc` (unset: `jpeg`, as before): `PreviewMosaic` (`src/media/mosaic.cpp`) is an NV12 canvas in device memory when a CUDA device is visible (`cudaMallocPitch`), else in host memory. The layout (`mosaicLayout`) puts the channels at 640×360, three a row, above the cameras at 480×270, four a row, as wide as the widest row, scaled down to fit 1920×1080 (8 channels and 12 cameras: 364×204 and 274×154); edges even. Every house grain up to 30 a second is drawn, every second one above (`mosaicStep`: 25 at 50p). The drawing is done where the picture already is: a camera's reader draws its tile right after `gpuEncodeV210` from the 8-bit planes it just unpacked (phase 1 only), a channel's playout thread after `gpuRenderFromJpeg` from its output planes; one kernel per tile on the thread's own stream, an area average of up to 8×8 samples per pixel, no sync (the thread's next work on that stream comes after it). A picture that is only on the host (no GPU, a black or idle grain, the CPU fallback of render, synthetic and HFR cameras through `ingestVideo`) is point-sampled on the CPU into a tile and copied up (`gpuCopyRows`) or into the host canvas under a mutex. Each tile has one writer and nobody waits: a tile can show parts of two pictures in one encoded frame. `PreviewPublisher` (`src/ops/publisher.cpp`, from mxl-multiviewer 1.4.0 and the FlowXer engine prototype) runs its own thread at the mosaic rate: `h264_nvenc` on `AV_PIX_FMT_CUDA` frames in the runtime's primary context (`gpuContext()`: `cuCtxGetCurrent` through `cudaGetDriverEntryPointByVersion`, so no libcuda link; FFmpeg's own `primary_ctx` refuses a context created with `cudaDeviceScheduleBlockingSync`), the canvas copied into the frame on the GPU; CBR 5 Mbit/s, preset p1, tune ull, no B-frames, one-second GOP, SPS/PPS out of band, an IDR on every new connection. Without a device canvas, or when NVENC does not open (no `video` driver capability, no NVENC), libx264 (`ultrafast`, `zerolatency`) encodes the canvas copied to the host, and `preview_nvenc_unavailable` gives the reason once. RTSP over TCP to MediaMTX, 2 s socket timeout; a failed connection is tried again every 2 s, a failed encoder every 5 s. FFmpeg's warnings go to this log (`ffmpeg` events) once the publisher exists. Camera and channel JPEGs answer 404 in this mode (never both); clip thumbnails and the shotbox stay JPEG. The UI (`web/src/preview.js`) opens one WHEP session per page when a picture first needs it, keeps it, and connects again 2 s after it drops; `LivePicture` shows its tile of that stream: its box gets the tile's aspect ratio (`overflow: hidden` as before), the `<video>` fills it with `object-fit: fill` and a transform `scale(W/w, H/h) translate(-x/W, -y/H)` so only the tile shows. CSS `object-view-box`, the crop the task named, is Chrome and Edge only (Firefox and Safari show the whole mosaic, seen with mxl-multiviewer 1.4.0), so the transform is the only crop; with `object-fit: contain` in a box of another aspect ratio a strip of the neighbouring tile showed. Measured on the lab (README "Previews").
42. **Preview contract** (1.4.0, platform §11.5 / D-185): as mxl-webrtc-monitor 1.3.0 §5.7 and mxl-multiviewer 1.4.0. `PREVIEW_PUBLISH_URL` empty: own mode, the image's MediaMTX runs as a child (`src/ops/child.cpp`, from the monitor: fork and exec of `mediamtx <REPLAY_STATE_DIR>/mediamtx.yml` from `PATH`, `PR_SET_PDEATHSIG` SIGTERM, own process group, restart 1 s after an exit doubling to 10 s, SIGTERM then SIGKILL after 3 s on shutdown). It is started before the engine, while the process is small (fork copies the page tables). The generated config has RTSP on `127.0.0.1:MEDIAMTX_RTSP_PORT` over TCP only, WHEP and ICE (UDP and TCP) and low-latency HLS on all addresses, ICE host `NMOS_HOST_ADDRESS`, and no API, metrics, RTMP, SRT or MoQ: the replay needs neither viewer counts nor path state, and fewer ports. Port block 8854/8689/8688/8489: the monitor has 8554/8889/8888/8189 (+9997/9998), the FlowXer engine 8654/8989/8988/8289/9897, the multiviewer 1.4.0 8754/8789/8788/8389 (its branch `feat/webrtc-preview-widgets`). A collision with `WEB_PORT` or the NMOS ports exits 78. Set: shared mode, publish there, start no MediaMTX. `/readyz` does not wait for MediaMTX: the preview is not what the replay is for. No aliases (the replay had no MediaMTX settings before). `PREVIEW_PUBLISH_URL` must not carry credentials (it is exported). The publish state is the RTSP muxer's: `connecting` until the first packet went out after ANNOUNCE/SETUP/RECORD, `publishing`, `error` with FFmpeg's message until it publishes again. MediaMTX 1.20 answers the first HLS request with a redirect (`?cookieCheck=1`); the integration test follows it.
43. **Widgets** (1.4.0, specification §8.7): `/widget/transport` and `/widget/clip-list` serve the same embedded page as `/`; `main.js` mounts `WidgetPage.vue` for `/widget/*`. The widgets use the store (WebSocket status, clip polls) and the existing `Segmented` and `ChannelPicker`; `transport` has its own compact speed fader (the LSM's has reverse and the wheel). Cue is *Go IN* (back to IN, paused; disabled without an IN mark). Load in `clip-list` is the shotbox click (`POST /api/v1/shotbox/{id}`): it cues, a second click plays, as on the shotbox page (with `REPLAY_PLAY_ON_FIRST_CLICK` the first click plays). `/widgets` answers CORS for an Origin listed in `WIDGET_FRAME_ANCESTORS` (as the multiviewer; the monitor 1.3.0 has none) and `Vary: Origin`. `HttpResponse` carries extra header lines for these routes.
44. **Output resyncs are counted** (1.4.0). `PlayoutGrid` (`src/playout/scheduler.cpp`) is the playout loop's grid of deviation 24 as a struct: more than two grains late, or ahead of the clock, continues at the current grain and counts a resync (`output_resyncs_total{channel}`, 0 from the start). `output_resync` is logged for the first one and then at most every 10 s with the count since the last line and the last jump. Every run on the lab showed one or two at the start (3–11 grains: the first grains create the CUDA and nvJPEG state).
45. **A stalled camera audio is logged** (1.4.0; the open point of deviation 40). `AudioWatch` (`src/mxl/io.hpp`) counts video frames recorded without audio samples since the last frame with them; `REPLAY_INPUT_STALL_S` worth of frames logs `recording_audio_stopped` (`flow_missing`: the audio flow cannot be opened; `no_samples`: the read gave none), the next frame with samples `recording_audio_resumed` with the gap. Counting frames instead of time keeps a pause of the video itself (`recording_stopped`) from counting as an audio stall. Not watched: an audio receiver that is not connected or not 48 kHz.

## Operating points

Taken from Futatabi `flow.h`:

| Preset | Futatabi point | Finest level | Variational |
| --- | --- | --- | --- |
| `fast` | 1 | 3 (1/8) | no |
| `balanced` | 3 | 1 (half) | yes |
| `quality` | 4 | 0 (full) | yes |

Weights match Futatabi: alpha 1, delta 0.25, gamma 0.25, five SOR iterations, omega 1.8, outer iterations = pyramid level + 1.

## Process

One process. Each playout channel has a thread that renders one grain per house period on the TAI grid and publishes it when libmxl is linked. HTTP and nmos-cpp use their own threads. The recorder runs on the ingest path (MXL reader thread, or the synthetic generator).

Exit codes: 0, 75 (storage or unexpected failure), 78 (config, including a buffer that does not fit), 143 (SIGTERM).
