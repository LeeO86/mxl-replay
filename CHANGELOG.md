# Changelog

## 1.8.2 (unreleased)

- Fix: after a settings save with `NMOS_TAGS` in the environment, the replay could not start again (exit 78, `config file has a non-string key`, in a loop). The save wrote `REPLAY_STATE_DIR/config.json` correctly, with `NMOS_TAGS` as JSON inside an escaped JSON string, but the reader ended a value at the first `"` and did not know `\"`. The state file (and `REPLAY_CONFIG_FILE` in JSON) is now read with replay's JSON parser: `\"`, `\\`, `\uXXXX` and JSON inside a string round-trip. `NMOS_TAGS` is read with it too (`\n` and `\u` escapes in tags were kept as letters).
- A state file that cannot be read or loaded no longer stops every start: it is renamed to `config.json.bad`, logged as `state_config_invalid` (`path`, `error`), and the replay starts with the environment, `REPLAY_CONFIG_FILE` and the defaults. An empty or blank state file counts as broken too. An older `config.json.bad` is kept: the new one is `config.json.bad-<UTC time>`. An invalid environment or `REPLAY_CONFIG_FILE` still exits 78.
- The state file is written durably: a temp file, `fsync`, rename, `fsync` of the directory (a power cut leaves the old or the new file, not an empty one).
- Stricter: 1.8.1 accepted a trailing comma (`{"A": "1",}`) and other non-JSON in a JSON config file; 1.8.2 refuses it. In `REPLAY_CONFIG_FILE` that exits 78; in the state file it is moved aside.
- The state file keeps only the keys the UI or the API set (*Play on red light*, the idle playlist, a config import), not the environment's or `REPLAY_CONFIG_FILE`'s. 1.8.1 saved every key that was set, so a key removed from the environment kept its old value. Precedence is unchanged (environment, `REPLAY_CONFIG_FILE`, the state file, the defaults); a key that is no longer in the environment now falls back to its default unless the UI set it. At start, keys in the state file that the environment or `REPLAY_CONFIG_FILE` sets are dropped from it and logged (`state_config_platform_keys_dropped`, `keys`), and the file is written again; a key from a 1.8.1 snapshot that is no longer set anywhere cannot be told apart from a UI setting and stays. The config export still has every key that is set.
- New tests: a round trip of values with quotes, backslashes, unicode and JSON in a string, other escapes and invalid files; `NMOS_TAGS` escapes; a settings save with `NMOS_TAGS` in the environment that starts again; a broken, an invalid and an unknown-key state file moved aside; the environment over the state file. `tests/integration/state_config.sh` (CI): a save and a restart with `NMOS_TAGS` in the environment, then a cut-off `config.json` moved aside at start.

## 1.8.1

- Fix: an upload at another frame rate than the house's kept its frames 1:1 at the house rate, so it played at the wrong speed and lost the audio after its shortened end. In a 50p house, a 2 s 25p file became a 1 s clip (`out_ns` − `in_ns` 0.98 s) with only its first second of audio. Uploads are now converted to the house rate by their timestamps: each house frame shows the source frame whose start is nearest to it (the earlier one on a tie). A 25p file repeats each frame in a 50p house, a 50p file drops every second one in a 25p house, and 29.97 maps to 25 by the same rule. Equal rates stay 1:1 under timestamp jitter of up to half a period. The duration stays, and the audio (already 48 kHz for the whole file) stays in sync. A still image is still one frame.
- A repeated source frame is kept once in memory and JPEG-encoded once (a 25p upload in a 50p house no longer needs twice the RAM).
- A frame without a timestamp in a file with timestamps keeps its place: it follows the previous frame by that frame's duration (else the stream's frame period).
- Fix: an upload whose video has no decoder or no pixel format (e.g. an AVI with an unknown codec) aborted the process inside `sws_getContext`. It now fails with 400 and a reason (`unsupported video: no decoder for …`, `… cannot convert <format> <size> to the house format`).
- Fix: an upload's audio in a 29.97 house was sliced with the frame's own sample count times its index instead of the cadence (1601/1602 samples), so it drifted by up to a frame's worth of samples.
- New unit tests: the frame-rate conversion (25→50, 50→25, 29.97↔25, 1:1, ±3 ms jitter at 50p and 25p stays 1:1 over 500 frames, a single short frame), the source clock (frames without timestamps), 25p / 50p YUV4MPEG2 uploads through FFmpeg (50 stored frames for 100 house frames), and the unknown-codec AVI.
- The Compose and Kubernetes examples use the `1.8.1` image.

## 1.8.0

- Interlaced video: replay records and plays 1080i. `REPLAY_FORMAT=1080i25` (the house format) or `1080i2997` (also `1080i29.97`; the number is the frame rate, as in mxl-test-player's `PLAYER_FORMAT`; top field first only, `bff`, `1080i50` and other rasters than 1920×1080 exit 78 with a hint). The flows follow the [shared MXL interlaced convention](https://github.com/LeeO86/mxl-multiviewer/blob/main/docs/mxl-interlaced.md).
  - Inputs are recorded as frames: an `interlaced_tff` camera at the house frame rate is read field by field and grains 2k (top field) and 2k+1 are woven into frame k, stored at the frame rate like a progressive frame. Clips, positions, jog and slow motion work on frames. A progressive camera at the house frame rate is recorded too.
  - Outputs: each channel writes each frame as two fields (`interlaced_tff`, grain 2k the even lines, 2k+1 the odd lines), so downstream sees 1080i with the field order of the recording. The ANC timecode flow runs at the field rate (declared 50/1 or 60000/1001): grain 2k with F = 0b10, grain 2k+1 with F = 0b11 and the field mark (bit 59 at 25 frames, bit 27 at 29.97, SMPTE ST 12-1), the frame's timecode in both. The 29.97 timecode stays non-drop-frame.
  - NMOS: the video receivers' caps list `progressive` and `interlaced_tff` in an interlaced house, with `grain_rate`, `frame_width` and `frame_height` limited to the house's (still only `progressive` in a progressive one); the video flows say `interlaced_tff` at the frame rate, the data flows and sources the field rate. The flow IDs change with the format, as for any format change.
  - Refused visibly as in 1.7.1 (route state `unsupported`, `mxl_video_unsupported`, `record_unsupported_total{camera,reason}`), with new reasons: `interlaced_bff` (bottom field first), `interlaced_rate` (an interlaced flow at another frame rate), and in an interlaced house `rate` (a progressive flow at another rate, e.g. a 1080p50 camera, which stalled with rising drops) and `raster` (another `frame_width`/`frame_height`). Progressive houses and native HFR cameras do not check rate yet (a separate change). An interlaced flow in a progressive house stays `interlaced`: there is no interlaced ↔ progressive conversion.
  - Known limitations: jog and positions are whole frames (two fields); field-accurate jog and field-based slow motion are not supported. A paused or slowed frame shows both its fields, so fast motion combs, and `blend` and `interpolate` work on the woven frames.
- `REPLAY_FORMAT` rates with a dot (`29.97`, `59.94`, `23.98`) are read as 30000/1001, 60000/1001 and 24000/1001; `1080p29.97` was 29/1.
- New unit tests: weave and unweave for top and bottom field first (grain 2k row i = frame line 2i for tff, 2i+1 for bff), a 1080i v210 round trip, the format tokens (1920×1080 only), the input mode per flow definition (`rate`, `raster`), the receiver caps, and engine passes in `1080i25` (frames at 40 ms, one ANC grain per field with F = 0b10 and 0b11, field mark bit 59) and `1080i2997` (field mark bit 27).
- Lab (mxl-test-player 1.2.4 `PLAYER_FORMAT=1080i25` into a `1080i25` replay, A16, channel 1 live): the `field_order` pattern's first-field stripe (luma 691) and second-field stripe (250) came out of the replay on the even (688) and odd (248) grains, through JPEG; ANC grains alternate F = 0b10 / 0b11 at 50/1. 25.01 frames/s recorded, 0 drops, 0 resyncs; `1080i2997` 29.97 frames/s. Weave and unweave cost 0.48 ms per 1080i frame each (a line-by-line copy, about a `memcpy` of the frame: 1.2 % of one core per camera and per channel at 25 frames/s); the replay process took 17.1 % of a core against 14.5 % for the same chain at 1080p25. bff, 1080i29.97 into a 1080i25 house, 1080i25 into a 1080p50 house, 1080p50 and 720p25 into a 1080i25 house were refused with `interlaced_bff`, `interlaced_rate`, `interlaced`, `rate` and `raster`; the 1080i25 house's receiver caps list `grain_rate` 25/1 and 1920×1080.
- The Compose and Kubernetes examples use the `1.8.0` image.

## 1.7.2

- Fix: the ANC timecode grain starts at the RFC 8331 Length field, as MXL stores it. MXL (docs/Architecture.md, `video/smpte291`) keeps the RFC 8331 payload from the Length field on; the RTP header and the extended sequence number are not stored. Replay wrote a 2-byte sequence number first (the layout copied from mxl-test-player), so Length was at byte 2 and the ATC packet at byte 8, and a reader that follows MXL (mxl-st2110-gateway ANC egress, MXL's `mxl-data-probe`, gst-mxl-rs) read the sequence number as Length. Now Length is at byte 0, ANC_Count at byte 2, the F bits at byte 3 (unchanged values), reserved to byte 5 and the packet at byte 6; the packet itself is unchanged and the sequence number is gone. Replay's own decoder reads the new layout; grains written by an older version (a stale data flow) are no longer decoded.
- New unit test: the grain bytes of a progressive LTC packet and of a field-2 VITC1 packet equal reference vectors from mxl-st2110-gateway's ANC codec (`codec::serialiseGrain`), the same vectors as mxl-test-player 1.2.4. Checked once against the gateway's parser: no parity or checksum errors.
- The Compose and Kubernetes examples use the `1.7.2` image.

## 1.7.1

- Fix: an interlaced camera input recorded nothing while its route said `running`. MXL keeps an interlaced flow as fields (half the lines, at twice the declared rate); the recorder read it at the frame rate, dropped every grain as too small for a frame, and still set the route to `running`. Now the video receivers' NMOS caps say `interlace_mode` `progressive` (BCP-004-01), so a controller that checks caps does not route an interlaced sender, and a routed flow whose `flow_def.json` is not progressive is not read: the route state is `unsupported` (red in the UI, `video_states` in the status), `mxl_video_unsupported` is logged once (`camera`, `phase`, `flow`, `reason` `interlaced`) and the new counter `record_unsupported_total{camera,reason}` counts it once per flow. The flow is checked again once a second, so one made again as progressive is recorded. Recording interlaced inputs is not supported (an open design question).

## 1.6.1

- Fix: an NMOS IS-05 activation of a camera receiver could be lost. ## 1.6.0

- Playlist transitions: an entry has a transition into it, `cut` (as before) or `mix` over `transition_frames` (1–250, default 25), and an audio crossfade over `audio_frames` (−1, the default: as the mix, and 2 frames on a cut, so the join does not click; 0: the audio cuts). The two entries overlap by the longer of both; the channel moves to the incoming entry when the transition starts. Each grain of a mix blends the two entries' nearest frames at `(k+1)/(N+1)` (GPU: the blend path without a flow; one extra JPEG decode per grain of a mix). The audio crossfade is equal power (sin/cos per sample: two entries are uncorrelated programme, so the loudness stays even; a linear fade dips 3 dB). A mix needs *next* with auto-advance (or the loop wrap, or the idle playlist), else the join cuts. Status per channel `transition`; metric `transitions_total{channel,kind}`; log `transition`. The countdowns and `duration_ns` take the overlaps off.
- Own audio per entry (`own_audio`, default on): off, the entry is silent and only the aux track plays.
- An audio aux track per playlist: `aux` `{source, level_db, loop, fade_out_frames, duck_db, attack_ms, release_ms}` (defaults "", 0, true, 50, −12, 200, 500). The source is a clip's audio or an audio item. It plays from the playlist's start at 100 %, loops or stops at its end (5 ms edge fades), pauses with the channel, fades out over the playlist's last `fade_out_frames` (a looped playlist does not fade) and ducks by `duck_db` while an entry's own audio plays. Status per channel `aux` (`source`, `gain_db`, `ducked`, `position_ns`).
- Audio items: an upload without a video stream (WAV, MP3, AAC, FLAC, anything FFmpeg decodes) becomes an audio item `audio-N` (48 kHz stereo float in the library), `POST /api/v1/uploads` answers `kind`. `GET /api/v1/audio`, `GET`/`PUT`/`DELETE /api/v1/audio/{id}`. The Library page lists them; the upload takes audio files.
- Playlists page: per entry the clip's IN thumbnail, the transition in (Cut/Mix, frames, audio frames) and own audio; an *Aux track* panel. The `playlist-editor` widget: IN thumbnails, a transition preset (Cut, Mix 12/25/50), own audio, the aux source and level.
- The catalog gets the new columns (and an `audio_items` table) when it opens an older one; the config export and import carry the entry and aux fields.
- Fix: an upload's audio at another rate than 48 kHz (44.1 kHz) was converted with room for only the input's samples, so the resampler held the surplus back to the end of the file (and dropped it); every output sample is kept now.
- Lab (A16, red / 1 kHz into green / 400 Hz): a 25-frame mix's 26 output grains equal the blend reference on every grain (read from the output flow); the largest sample step at the join 0.0177 (the two tones' own maximum 0.0178: no click); an aux bed at −18 dBFS ducked to −30 in 100 ms under a clip with its own audio and faded out over the last 50 frames.
- Fix: the GPU decoded the second JPEG of a pair while the first decode's work was still queued with the same nvJPEG state; a mix of two cameras showed parts of frame B in frame A. The playout now waits for A before it decodes B (only when it decodes both).
- A looped playlist plays over and over: with `loop` on, its last entry's `freeze` or `black` wraps to the first entry and plays on; an entry's own `loop` or `return-to-live` still applies. The Playlists editor shows "↻ Loop: wraps to the first clip" on that entry.
- Shotbox countdowns: every channel shows the playing time to its clip's OUT and to its playlist's end, at the speed set (red under 5 s while it plays). The playlist ends after the first entry that does not end with *next*, else after its last (a looped playlist: the end of this pass); the time an entry waits cued is not counted. Status per channel `clip_remaining_ns`, `playlist_remaining_ns` (null when there is nothing to count, or at speed 0 or with a looping entry), `playlist_loop`. The transport widget shows them too (its `min_size` is now 480×180).
- Idle playlist per channel: `CH<n>_IDLE_PLAYLIST` (Settings *Idle playlist*, `POST /api/v1/channels/{n}/idle-playlist {"playlist": "<id>"}`, `""` clears it; kept in the state directory). It plays looped when it is set on an idle channel (stopped, ended or black; a live, scrubbed, playing, cued or paused channel keeps its shot and the idle playlist starts at the next clip end, stop or playlist end) and at start, when the channel is stopped, and when a clip or a playlist ends (in place of *freeze*, *black* and the end of a playlist; *loop* and *return to live* keep theirs). In it every clip plays on: the entries' end actions and auto-advance are not used. Status `idle_playlist`, `idle`; log `idle_playlist`. Deleting the playlist clears it.
- Stop: `POST /api/v1/control {"action":"stop"}`, transport command `stop`, *Stop* in the shotbox and the transport widget. It plays the idle playlist; without one the shot ends where it stands (ended, paused).
- Playlists can loop: `loop` in `POST`/`PUT /api/v1/playlists`, the playlist answers, the catalog (a column added to an existing catalog) and the config export; *Loop* on the Playlists page.
- Shotbox filter: all, clips or playlists (kept in the browser). A playlist's button stacks the thumbnails of its first three clips; `GET /api/v1/playlists` lists each playlist's `clip_ids`.
- Widgets: `playlist-editor` (a playlist's entries: add a clip, reorder, speed, end action, remove; saved at once; `playlist` or a picker), `playlist-player` (`channel`; pick a playlist or `playlist`; Cue, Play/Pause, Stop, the countdown to its end, Loop on/off) and `timeline` (`channel`; the LSM tab's timeline with seek, clip marks, IN/OUT, Go IN/OUT, ±1 frame). `transport` takes `clip=true` (IN, OUT, Go IN, Go OUT, Create clip) and `presets=false`; its defaults look as before. One list of widgets serves `/widgets` and `/widget/<id>`, which checks every param of it (400) and answers an id not in it with 404.
- `POST /api/v1/playlists/{id}/cue {"channel"}` cues a playlist's first clip, paused (as `/play` without playing).
- Slow motion on the GPU: the two JPEG frames of an interpolated or blended grain (and of an optical flow) are decoded with one nvJPEG state, and the second decode could refill its staging buffers while the first one's copies were still queued, so parts of frame B could show in frame A. Between consecutive frames of one camera this is hardly visible (they look alike), but it is wrong. The decoder now waits for A before it decodes B, only when both are decoded in the same call (the start of a play, a jump, an angle change). Found while testing playlist mixes, where two different cameras made it obvious.
- Known limitations: during a long mix the clip countdown counts to the outgoing entry's OUT and does not reach 0 before the channel moves on (the playlist countdown is right); in a slow-motion mix the outgoing side's audio advances one frame per grain; an aux audio item deleted while it plays stops without a fade.

## 1.4.1

- Slow motion in `interpolate` no longer makes a channel late when the GPU is busy. On the platform the replay shared its RTX A4000 with another process, and channel 1 resynced about 24 times a minute (3 grains each, visible downstream): each new pair of source frames had its optical flow computed inside the playout, and one flow took more than two grains. Flows are now computed ahead, by a worker per channel, for the pairs the next 8 grains need (a paused channel: its own pair, and the first pairs of a play); a command (cue, play, speed, angle, mode) starts them at once. The playout never waits for a flow: a grain whose flow is not ready yet is blended. The same flows as before (same kernels, same cache keys); without load steady play at 25 % and 50 % interpolates every grain.
- `mxl_replay_interpolation_fallbacks_total{channel}` counts the blended grains, and `interpolation_fallback` logs them (at most every 10 s, with the count and `flow_ms`, the last flow's time). `mxl_replay_frame_gpu_seconds{channel,stage="flow"}` is the GPU time of each flow.
- Without load a few fallbacks remain: the first 1–3 grains of a play that starts right after its cue (one flow takes 22 ms on the lab's A16), and a few grains when the replay alone saturates the GPU (75 % on an A16: 16 of 1100 grains; 1.4.0 resynced 79 times there).
- GPU stream priorities: the playout first, then the recording, then the flows and the preview copies. A blended grain is the degradation under load; the recording does not drop. With flows above the recording, the lab load made the recorder drop 20 grains and the live channel resync 87 times.
- `REPLAY_ALLOW_CPU_INTERP` (no GPU: tests, harness) computes its flows ahead the same way; `flow_cache_miss_total` is gone.
- `tests/integration/preview.sh`: the `statusz` helper prints a tuple for an `a, b` expression (as mxl-multiviewer 1.4.1).
- Lab (A16, 4 cameras 1080p50, 2 channels, channel 1 from 20 s back, a CUDA load in another container on the same GPU, busy/idle ms; 30 s): resyncs 1.4.0 → 1.4.1 without load at 50 % 0 → 0, 25 % 0 → 0, 75 % 79 → 0; under 10/5 at 50 % 134 → 0, 25 % 0 → 0; under 40/2 at 50 % 221 → 0, 25 % 41 → 0. Blended grains with 1.4.1 (after the first 2 s): 156 of 750 at 50 % under 10/5, 328 of 750 under 40/2, none at 25 %. GPU time per flow 22 ms without load, 39 ms under 10/5, 57–59 ms under 40/2. `blend`, `repeat` and live under load: no resyncs; no recording drops in any run. Paused on the same positions of a real clip, 1.4.1 and 1.4.0 pictures are 36–55 dB apart (PSNR), two 1.4.0 replays 39–63 dB (the flow is not bit-exact between runs).

  - The log has `recording_stopped` (`camera`, `phase`, `reason`: `no_grains`, `invalid_grains` or `flow_missing`) once when a connected camera has recorded nothing for `REPLAY_INPUT_STALL_S` (new setting, default 2 s), and `recording_resumed` with `gap_ms` when it records again.
  - `write_bytes_per_second` is what the recorder wrote since the previous scrape (0 when nothing records). The write test at start, which it showed before, is now `storage_measured_bytes_per_second`.
- Recording already resumed by itself when grains came back (also after the platform's link outage, without a restart). The lab confirmed it for a writer that pauses, stops, is killed or restarts, for fabrics agent restarts, a source agent stopped for 20 s, and mirror flows deleted and created again by the agent (new inodes). One thing did not come back: the camera's audio. After a writer restart or a re-created flow the recorder stayed on the deleted audio flow and stored the following frames without audio, while the audio receiver still said `running` (lab: recorded audio level 0.089 → 0 after a test-player restart with a 15 s gap, and → 0 after the fabrics agent created its mirror flows again). It now opens the audio flow again and the audio is back with the video (0.089 before and after).
- Lab (2 cameras, own test player or two fabrics agents over tcp), 1.3.1 → 1.3.2: writer paused 15 s: silent, write rate stuck at 54.3 MB/s → `recording_stopped` `no_grains` after 2 s, write rate 0.0, age growing to 14.1 s, `recording_resumed` `gap_ms` 15096, 50 frames/s again; writer stopped 15 s (flows deleted, created again): silent and audio lost → `flow_missing`, `gap_ms` 16970, audio kept; fabrics source agent down 20 s: silent → `no_grains`, `gap_ms` 22076; mirror flows deleted and created again by the agent: silent and audio lost → `flow_missing`, `gap_ms` 22595, audio kept. No drops in any run.

- Grains a source never wrote no longer count as dropped. A camera that connects before its writer writes (the test player creates its flows first, then starts its outputs; a source that restarts) waits at its first grain. 1.3.0 then counted every grain up to the writer's first one, one by one as each never-written slot left the flow's one-second history, and started recording a second late from the oldest grain, where the first encodes cost a few real grains. That was the "dropped 50 at start" on the platform. Now an unwritten grain behind the writer's head is skipped at once, and a grain that left the history while the reader waited for it is not counted. A source that stops for more than a second no longer counts either. A recorder that falls behind its source still counts every grain it missed. Lab, 2 cameras on a test player, per camera: player started after the replay 3–15 → 0 drops (5 starts), player restarted 2–10 → 0, player frozen 3 s 106–107 → 0, replay frozen 2 s 57–65 → 55–64 (real, still counted). No settings change.

## 1.2.3

- The GPU path waits for the GPU in a blocking sync instead of spinning a CPU core. CUDA's default scheduling spins while the machine has spare cores, so every `cudaStreamSynchronize` of every channel and camera thread held a core busy. Lab host (2× Xeon Gold 6136, A16), 4 cameras recording, channels interpolating at 0.5×: 2 channels 3.79 → 0.82 cores, 4 channels 7.37 → 0.89 (6.5 cores had been inside libcuda), 8 channels 12.11 → 0.93; 4 channels at 1× 3.29 → 1.75. ## 1.2.2

- Without a GPU the replay records every frame. The CPU JPEG encode ran under the engine lock, so the cameras waited for each other: on the lab (2× Xeon Gold 6136, 4 cameras 1080p50, no GPU) each camera recorded about 11.5 and dropped about 45 grains per second. A camera with one phase now encodes on its own reader thread, straight from the v210 grain into the stored JPEG (no 16-bit frame, codec and buffers kept per thread). 4 cameras + 2 channels at 1×: every grain recorded, 3.8 cores; 4 cameras + 4 channels blending at 0.5×: every grain recorded, 50 grains/s per output, 6.0 cores.
- CPU playout: an exact frame (live, 1×, repeat) is decoded straight into the output grain; only a blend decodes two 16-bit frames (before, every frame decoded frame B as well). The blend runs without the engine lock, in integer steps of 1/1024, in place.
- Idle and black channels use one cached black grain, and thumbnails of the CPU path are refreshed every 10th frame: two idle channels went from 0.90 to 0.30 cores (with a GPU).
- Documentation: a dedicated local NVMe for `REPLAY_STORAGE_DIR` is a requirement (README, specification §4.3 and §10). The OS disk, rotating disks and network storage are not supported.
- The unit test "disk ring reads while it writes" no longer fails when the writer finishes before the reader thread has run.

## 1.2.1

- A live channel waits up to half a frame for its frame when the recorder stores it late (while the camera records close to live). Without the frame, the channel showed M−3 and then jumped to M−1. Measured on the lab after the release: the late frames come from the storage. With the buffer in RAM, 1.2.0 showed none in 60 windows of 80 frames. On the lab's SAS disk, where one `write()` can block the recorder for 20–30 ms, 1.2.0 and 1.2.1 both showed a few (57/60 and 56–58/60 clean windows), so the wait does not cover a slow disk. Keep the buffer on a dedicated NVMe.
- After a missed camera audio read, the recorder keeps waiting for the audio for three more frames before it falls back to one waiting read per 50 frames. One late packet no longer costs up to a second of audio.

## 1.2.0

- Camera audio is recorded and played out. 1.1.0 accepted connections on the `<camera> Audio` receivers but never read them, so playout audio was silent. The recorder now reads, for every video grain, that frame's 48 kHz samples from the camera's audio flow and stores them with the frame (first two channels, mono doubled; the receiver reports `unsupported` for another sample rate). HFR cameras take their audio with phase 1. The playout audio flow is written at the sample index, one ring per channel. Before, it was written at the video grain index into the first channel's ring only.
- Uploads are stored again when the cameras record. Since 1.1.0 an upload went to camera 1's buffer at TAI 1 ns onward, and that buffer only appends, so once camera 1 had recorded anything the frames were dropped while the clip was still created. Uploads now go to their own library buffer (`REPLAY_STORAGE_DIR/library/frames`, camera `0` in the clip list), which keeps a segment only while a clip uses it. Clips uploaded with 1.1.0 keep camera 1.
- The start no longer waits for the re-index before HTTP. `/livez` answers at once; `/readyz` and the API answer 503 (`{"status":"indexing"}`) until the retained segments are indexed, and NMOS and MXL start after that. 4 cameras × 1.5 h are about a million small reads.
- `REPLAY_PROTECT_MAX_PCT` counts the segments that clips keep. A clip keeps whole segments, but the cap counted only the protected frames, so clips could keep much more than the cap.
- Frames that cannot be written (full disk or I/O error) are counted per camera in `mxl_replay_storage_write_failed_total`, and the log has one `segment_write_failed` per run of failures and a `segment_write_recovered` with the count. On a full disk every frame also left an empty segment file behind; it is removed now.
- Disk I/O runs outside the engine lock. Each camera buffer has its own lock that is never held during a read or write, and the engine lock is released while recording writes, while a channel reads its frames and audio, and while a clip is exported. A slow disk used to stall every channel. A channel playing at 100 % reads one frame per output frame instead of two, and the audio no longer reads the frame's JPEG.
- The recorder no longer stalls at every segment rotation. Starting the writeback of the finished segment (`sync_file_range`) blocked the recording thread for 0.7–1.0 s on the lab's SAS disk, every 10 s and on all cameras at once, close to the 1 s input history. Writeback, the page-cache drop and deletions now run on a background thread per buffer.
- Playout renders each output grain for its own time on the TAI grid. It rendered for the wake-up time, so a live channel sat between two recorded frames: it interpolated them (or blended, or repeated one of them), the audio repeated or skipped a frame when the wake-up time drifted across the half frame, and a grain index could be written twice. Live output is now the recorded frame two grains back, exactly.
- A camera's audio that is committed a little after its video is waited for (up to one frame) instead of being stored as silence, as long as the audio keeps arriving.
- Clip, upload and playlist ids continue after the catalog's highest id. They started at 1 on every start, so the first clips made after a restart replaced the clips that already had those ids (`clip-1`, `upload-1` …), while their ranges stayed protected.
- The buffers of cameras that are no longer configured are deleted at startup unless a clip uses that camera (`removed_camera_deleted`, or `removed_camera_kept` with the bytes).
- `/metrics` has the per-camera series the README listed: `record_frames_total`, `record_dropped_total`, `phase_missing_total`, `protected_bytes`, `disk_bytes`, and the new `storage_write_failed_total`.

## 1.1.0

- The replay buffer lives on `REPLAY_STORAGE_DIR` instead of in RAM. 1.0.x kept every JPEG frame of the buffer in memory (4 cameras × 1.5 h is about 420 GB) and wrote segment files that were never read. Frames now go to the segments only; memory holds an index of about 32 bytes per frame and a few open files, and playback reads the frames back from the segments.
- Disk use stays at the buffer duration: segments that are older than the camera's `BUFFER_HOURS` behind its newest frame are deleted, unless a clip touches them.
- A restart keeps the buffer and the clips: the existing segments are indexed again and the clips in the catalog protect their frames again. 1.0.x renumbered its segments from 0 on every start and overwrote them; those files are removed at the first start.
- The startup space check counts the buffer's own segments as available, so a second start with the storage kept no longer exits 78.
- NMOS senders and receivers carry their own labels (`<channel label> Video`, `Audio`, `Data`; `<camera label> Video`, `Audio`) instead of the node label, so a controller can address them by label. Default channel labels are unique: `PGM`, `PVW`, `CH3`, `CH4` … (every channel after the first was `PVW`).
- Camera status reports `disk_bytes` and `segments`.
- `REPLAY_ODIRECT` is ignored with a warning.

## 1.0.1

- GPU work no longer runs behind one lock. Every recorder input and every playout channel has its own thread, CUDA stream and nvJPEG state; the engine lock is released while a channel decodes, interpolates and downloads. Before, one thread encoded every camera and one loop rendered every channel in turn, both behind a single mutex. On an NVIDIA A16 (one GA107) four cameras now record at full rate while four 1080p50 channels interpolate at 0.5×; before, two channels left each camera at about 19 of 50 grains per second ([docs/benchmarks/README.md](docs/benchmarks/README.md)).
- Fewer GPU stalls and copies: device memory comes from the stream-ordered pool instead of per-frame `cudaMalloc`/`cudaFree` (which waits for the whole device), the v210 kernels run one thread per 6-pixel group instead of one per row, the MXL grain is page-locked for its upload, and a source frame still decoded from the previous output frame is not decoded again.
- The process raises its open-file limit to the hard limit. MXL keeps one descriptor per grain, and four cameras with four channels passed Docker's default of 1024 ("Too many open files"; cameras 3 and 4 never recorded).
- The MXL recorder keeps one reader per camera phase while its route stays the same and reads every grain since the last one. Before, it scanned the domains and created a new reader for each grain, recorded about 9 of 50 grains per camera at 1080p50, and counted none as dropped. Grains that leave the input ring before they are read now count in the camera's `dropped`. Each recorded frame carries the timestamp of the grain that was read (it was two grains later).

## 1.0.0

First stable contract for the platform. Settings, the HTTP API, and the shutdown behaviour below stay compatible until 2.0.0.

### Platform settings

New settings. Existing names still work.

- `REPLAY_STATE_DIR` (default `/config`) holds the catalog, imported settings, and IS-05 routes. A catalog found in `REPLAY_STORAGE_DIR` is copied here once.
- `NMOS_LABEL` sets the node label and the device label. When it is unset, the node label stays `HOST_ID` and the device label stays `MXL Replay`.
- `NMOS_TAGS` is a JSON object of string arrays added to the node and the device.
- `NMOS_HOST_ADDRESS` is the IPv4 address announced to other systems. `HOST_ID` remains the seed identity. If `HOST_ID` is an IPv4 literal and `NMOS_HOST_ADDRESS` is unset, that literal is still the announced address.
- `NMOS_QUERY_ADDRESS` defaults to `NMOS_REGISTRY_ADDRESS`. `NMOS_QUERY_PORT` defaults to `NMOS_REGISTRY_PORT + 1`.
- `MXL_HISTORY_DURATION` (nanoseconds, default `2000000000`) is written when the output domain is created.
- `MXL_CLEANUP_ON_EXIT` (default `false`) removes only this function's output domain on shutdown.
- `SHUTDOWN_TIMEOUT_S` (default `10`).

`NMOS_DNS_SD=false` still disables DNS-SD browsing and mDNS advertisement.

The default `MXL_OUTPUT_DOMAIN_ID`, when unset, is now the same UUIDv5 as the NMOS domain id (`mxl-replay/<NMOS_SEED>/domain`).

### API

- `GET /api/v1/config/export` returns one JSON document. There are no secret settings, so `include_secrets=true` adds nothing.
- `POST /api/v1/config/import` restores settings, clips, and playlists from that document.
- `/readyz` is 200 only after the node is listed on the Query API when a registry address is configured.
- A `WEB_PORT` or `NMOS_PORT` that cannot be bound exits 75.
- SIGTERM exits 143 after MXL readers and writers are released and the node is removed from the registry.
